# Evidence-led launch preparation

Prepared 2026-10-14. Nothing here authorizes a post, message, release, paid
promotion or deployment. The current branch is still an implementation pass;
comparative claims need a separate reviewed campaign.

## Seven-day preparation and optional launch sequence

| Day | Concrete work | Exit evidence | External action boundary |
| --- | --- | --- | --- |
| 1 | Select one verified local failure and its owned skill | Reproduce before/fix checks from gallery on a clean checkout | No post |
| 2 | Write a 15-second failure explanation and short reproducibility note | Only observed output and limits; sanitization review | No post |
| 3 | Run fresh selected-skill onboarding with a real novice if available | Time-to-first-result, error text and assistance needed, with consent | Invitations need explicit authorization |
| 4 | Fix installation/documentation friction observed in that session | A fresh install and actual command output | Local corrections may proceed |
| 5 | Prepare GitHub release text, relevant topics and one small demo page | Claims registry/readiness checks and links | Publishing and metadata changes need explicit authorization |
| 6 | Check the intended community's current rules; adapt the failure narrative | Maintainer affiliation disclosed, runnable artifact, no unverified speed claims | Human selects and authorizes actual post |
| 7 | If approved, share one relevant demonstration and answer real questions | Preserve actual feedback/issues; otherwise keep drafts ready | No automatic cross-posting or unsolicited messages |

## Thirty-day follow-through

| Window | Work | Evidence to keep |
| --- | --- | --- |
| Days 1–7 | Respond to authorized discussions and turn actionable reports into minimal fixtures | Original sanitized request, failure command, skill/runtime/package identity |
| Days 8–14 | Repeat onboarding with an experienced developer and a different project | Native activation, first useful artifact and friction; empty cells stay unknown |
| Days 15–21 | Resolve the highest-impact reproducible failure and retest its neighbors | Narrow before/after acceptance checks, source-to-decision trace, preserved regression |
| Days 22–30 | Review unresolved evidence gaps; decide whether a funded proof campaign is justified | Pin tasks/models/checkers, approve budget separately, publish only independently reviewed claims |

## Draft content kit

Use one mechanism per post, with a runnable evidence link and a stated limit.
Example cache narrative: “Read, write, read: the second read returned the old
value. We traced the warmed-cache branch, invalidated only the written key,
and kept a regression for the failing sequence.” This describes the local
fixture, not an actual customer incident or a normal-agent comparison.

For GitHub: issue/PR-style problem, changed behavior and check command. For a
short video: show actual terminal failure, scoped diff and passing command;
do not simulate an unrecorded UI or invent developer testimonials. For Reddit:
explain the failure and disclose authorship; first check the specific community
rules. For X/newsletters/Discord/Indie Hackers: use the same factual source,
adapt to the channel, and obtain posting authorization rather than starting a
distribution bot. Content slots for those channels are prepared; their current
community rules and access remain unverified.

supports relevant purpose/language topics;
[Show HN](https://news.ycombinator.com/showhn.html) asks for a real artifact
people can try; [HN submission guidance](https://news.ycombinator.com/newsguidelines.html)
must be checked for a proposed submission. The old
[Reddit self-promotion wiki](https://www.reddit.com/wiki/selfpromotion/)
explicitly says it is no longer updated, so its historical percentage rule is
not treated as current permission. Current channel-specific rules still need
checking immediately before any authorized post.

## Onboarding study protocol and privacy-respecting funnel

Use consenting participants and a clean test project; collect no credentials,
private source or transcript by default. One novice and one experienced
developer can each install one skill, choose a real task, attempt it unaided,
and explain where instructions stopped making sense. Record observed elapsed
time to first useful artifact, whether installation succeeded, actual check
output, assistance and misroutes. Let participants review and remove notes.
No participants were recruited and no study findings are claimed here.

Useful signals are consented successful installs and independently checked
first-task results, useful issue/PR contributions, and aggregate referrers only
where an existing site provides them. Public install counts, stars and forks
describe attention with their sampling limits; they are not effectiveness or
conversion evidence. No invasive tracking or guessed rates are proposed.
